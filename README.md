# MusicStream

Поиск метаданных композиций через **Deezer по умолчанию** и MusicBrainz по выбору.
Python 3.12+, uv, FastAPI; исходный код — `src/musicstream/`.

## Запуск (PowerShell)

```powershell
cd E:\MusicStream
uv sync
uv run uvicorn musicstream.main:app --reload
```

Для поиска Deezer контакт и API-ключ не нужны. Swagger UI:
http://127.0.0.1:8000/docs. Выберите `GET /api/search` → **Try it out**.

```powershell
# По умолчанию Deezer
Invoke-RestMethod 'http://127.0.0.1:8000/api/search?q=Rammstein&limit=2' | ConvertTo-Json -Depth 5
# Явный выбор Deezer
Invoke-RestMethod 'http://127.0.0.1:8000/api/search?q=Rammstein&limit=2&provider=deezer' | ConvertTo-Json -Depth 5
Invoke-RestMethod 'http://127.0.0.1:8000/health'
```

`q` обязателен; пустая строка и пробелы дают 422. `limit` по умолчанию 10,
допустимы целые значения от 1 до 25. `provider`: `deezer` (по умолчанию)
или `musicbrainz`; другие значения дают 422.

Запрос обращается только к выбранному провайдеру, без автоматического
переключения при ошибках. Для Deezer выполняется один запрос `/search`;
запросы деталей композиций и обращения к MusicBrainz не выполняются.

## Формат результатов

Ответ — JSON-массив с единой моделью для обоих провайдеров:

| Поле | Значение |
| --- | --- |
| `id` | ID композиции у выбранного провайдера, строка |
| `title` | Название композиции |
| `artist` | Имя исполнителя |
| `album` | Название альбома |
| `duration_seconds` | Длительность в секундах |
| `cover_url` | URL доступной обложки Deezer, предпочтительно самого большого размера |
| `isrc` | ISRC, только если присутствует в ответе поиска |
| `explicit_lyrics` | Метка Deezer `true`/`false`, если известна |
| `rank` | Популярность `rank`, полученная от Deezer |
| `musicbrainz_id` | Прежнее поле для совместимости; для Deezer — `null` |
| `source` | `deezer` или `musicbrainz` |

Отсутствующие данные равны `null`; пустая выдача — `[]`. ISRC может отсутствовать
в поисковой выдаче Deezer и тогда остаётся `null`. Значения `false` и `0`
сохраняются. **`explicit_lyrics: false` не гарантирует оригинальную
нецензурированную версию**; приложение не делает таких выводов.

Для MusicBrainz `id` совпадает с `musicbrainz_id`, длительность переводится
из миллисекунд в секунды с сохранением дробной части, альбом — первый доступный
релиз. Совместные исполнители объединяются с разделителями MusicBrainz.
Поля обложки, ISRC, explicit и rank для MusicBrainz равны `null`.

## Дополнительный провайдер MusicBrainz

Перед запуском укажите свой действующий контактный email или URL:

```powershell
$env:MUSICBRAINZ_CONTACT = Read-Host "Ваш контактный email или URL для MusicBrainz"
uv run uvicorn musicstream.main:app --reload
```

```powershell
Invoke-RestMethod 'http://127.0.0.1:8000/api/search?q=Queen&limit=10&provider=musicbrainz' | ConvertTo-Json -Depth 5
```

Контакт передаётся в `User-Agent: MusicStream/0.1.0 (<контакт>)`; должен
содержать печатные ASCII-символы. Он читается при запуске, после изменения
нужно перезапустить сервер. Файл `.env` автоматически не загружается.
Без корректного контакта только поиск MusicBrainz отвечает 503;
Deezer, `/` и `/health` доступны. Для MusicBrainz требуется доступ к его API
из сети сервера. Его запрос поддерживает синтаксис Lucene.

Общий ограничитель MusicBrainz сериализует запросы с интервалом между началами
не меньше секунды. Запускайте **один worker и один экземпляр сервера**:
ограничитель находится в памяти процесса. Для нескольких процессов потребуется
внешний общий ограничитель. `Retry-After` MusicBrainz учитывается перед
следующим запросом для HTTP 429 и 503.

## Ошибки

Для обоих провайдеров таймаут HTTPX — 10 секунд на каждую сетевую операцию;
клиенты создаются на время работы приложения и закрываются при остановке.
Автоматических повторов нет. Ошибки возвращаются как `{"detail": "..."}`
без содержимого ответа провайдера и внутренних исключений:

- 502 — ошибка сети, отклонённый HTTP-запрос, некорректный ответ или ошибка
  Deezer в JSON при HTTP 200;
- 503 — HTTP 429/5xx провайдера или отсутствие корректного контакта MusicBrainz;
- 504 — таймаут.

При HTTP 429 MusicBrainz возвращается `Retry-After`, по умолчанию 1 секунда.

## Веб-интерфейс

После запуска откройте **http://127.0.0.1:8000/app**. Страница использует
существующий `/api/search` с Deezer по умолчанию; отдельный frontend-сервер
и сборка не нужны. HTML, CSS и Vanilla JavaScript находятся в
`src/musicstream/static/`, ресурсы доступны через `/static/`.

Введите трек, исполнителя или альбом. Поиск начинается через 350 мс после
ввода; Enter и кнопка «Найти» запускают его сразу. Предыдущий незавершённый
запрос отменяется, устаревший ответ не заменяет новые результаты. Кнопки
с исполнителями под строкой поиска запускают поиск выбранного имени.

Показываются до 25 результатов: обложка, название, исполнитель, альбом,
длительность. Если обложки нет или она не загрузилась, остаётся нейтральная
иконка. Для пустой выдачи, загрузки и ошибки подключения предусмотрены
отдельные состояния; после ошибки можно повторить поиск.

Нажмите на название трека, чтобы выбрать источник воспроизведения.
YouTube использует видимый официальный плеер; подробности ниже в разделе источников.

Проверка вручную:

1. Введите `Rammstein`, дождитесь результатов и обложек.
2. Быстро измените запрос; в выдаче должен остаться последний запрос.
3. Нажмите Enter, выберите название трека и проверьте нижнюю панель.
4. Очистите поле — вернётся приглашение к поиску.
5. Проверьте страницу на узком экране и в режиме Offline инструментов
   разработчика браузера: при поиске должна появиться понятная ошибка.

Пути к ресурсам вычисляются относительно Python-модуля. Для запуска из
другой папки PowerShell используйте каталог проекта явно:

```powershell
uv run --project E:\MusicStream uvicorn musicstream.main:app --reload --reload-dir E:\MusicStream\src
```

`/`, `/health`, `/api/search` и `/docs` остаются доступны. Тесты `/app`
и ресурсов запускаются общей командой `uv run pytest -q`, в том числе
с изменённой рабочей папкой процесса.


## GitHub Pages: отдельная статическая публикация

Frontend можно разместить по адресу `https://<владелец>.github.io/MusicStream/`.
FastAPI остаётся локальным: GitHub Pages не запускает Python и не публикует
backend. Локальный `/app` по-прежнему использует API своего сервера.

### Сборка и проверка локально

Сборка использует только стандартную библиотеку Python, без Node.js/npm:

```powershell
cd E:\MusicStream
uv run python scripts/build_pages.py
uv run python -m http.server 8080 --bind 127.0.0.1 --directory dist
```

Откройте `http://127.0.0.1:8080/pages/`. Все ссылки на ресурсы в сборке
относительные, поэтому они работают и под `/MusicStream/` на GitHub Pages.
Каталог `dist/pages` должен отсутствовать или быть пустым до сборки.
Повторная сборка в непустой каталог завершается ошибкой без удаления файлов;
можно выбрать новый каталог через `--output dist/pages-preview`.

В Pages-артефакт попадают **только** `index.html`, `style.css`, `app.js`,
сгенерированный `config.js` и `.nojekyll`. Python, тесты, `.env`, `.venv`,
ключи, конфигурация сервера и Git-история в этот артефакт не включаются.
Исходники провайдеров могут стать видимыми отдельно, если сам репозиторий
сделать публичным; это не то же самое, что содержимое Pages.

### Настройка в GitHub

После проверки изменений и вашего разрешения на коммит и push в `master`:

1. Для бесплатного Pages на GitHub Free репозиторий должен быть публичным.
   До смены видимости проверьте отчёт по секретам и личным данным.
2. Откройте репозиторий **MusicStream → Settings → Pages**.
3. В **Build and deployment → Source** выберите **GitHub Actions**.
4. Откройте **Actions → Publish static frontend to GitHub Pages** и запустите
   **Run workflow** для `master`. Workflow также запускается при push в `master`
   с изменениями frontend, сборщика или самого workflow.
5. Если GitHub запросит настройку environment `github-pages`, разрешите
   развёртывания из `master`. Дождитесь успешных jobs `build` и `deploy`.
6. Откройте адрес, показанный в deployment; ожидаемый путь — `/MusicStream/`.

До настройки backend **не задавайте** переменную `MUSICSTREAM_API_BASE_URL`.
Сборка по умолчанию включает явный **демонстрационный режим**: поиск
отключён, запросов к API нет, вымышленные композиции не показываются.
Оформление и недоступная панель плеера доступны для просмотра.
Демонстрационный режим также включается, если конфигурация браузера не загрузилась.

### Публичная конфигурация API (для будущего подключения)

`src/musicstream/static/config.js` — конфигурация локального `/app`:
`apiBaseUrl: ""`, `demoMode: false` означает API на том же origin.
Сборщик не копирует этот файл: он создаёт отдельную конфигурацию Pages.
Никакой зависимости от `127.0.0.1:8000` в коде frontend нет.

Когда внешний HTTPS-backend будет отдельно настроен, укажите **публичный
адрес нашего backend** в **Settings → Secrets and variables → Actions →
Variables → New repository variable**, имя `MUSICSTREAM_API_BASE_URL`.
Используйте корневой адрес, например `https://backend.example.invalid`,
без `/api/search`, логина, пароля, токенов, query и fragment. Затем снова
запустите workflow. Приложение добавляет `/api/search` к этому адресу.
Адрес в `config.js` доступен всем посетителям — **это не место для секретов**.

Эквивалентная локальная сборка:

```powershell
uv run python scripts/build_pages.py --output dist/pages-api-preview --api-base-url https://backend.example.invalid
```

В будущем backend должен разрешать CORS для точного origin Pages
`https://<владелец>.github.io` (без `/MusicStream/`). HTTPS нужен для исключения
mixed content. В этой задаче CORS и туннель не подключаются, FastAPI не
открывается наружу. Браузер не обращается напрямую к поисковым API Deezer
или MusicBrainz: каталог доступен только через наш backend.

## Отдельная точка входа публичного API

Локальная разработка сохраняет прежнюю команду и все маршруты:

```powershell
uv run uvicorn musicstream.main:app --reload
```

Для будущего туннеля подготовлено отдельное приложение
`musicstream.public_api:app`. Оно использует тот же сервис поиска и провайдер
Deezer для метаданных; доступны `GET /api/search`, `GET /health` и
проверяемый `GET /api/audio/resolve` для поиска источника воспроизведения.
`/`, `/app`, `/static/`, `/docs`, `/redoc`, `/openapi.json` недоступны.
MusicBrainz остаётся доступен в локальном приложении; публичное разрешает
только Deezer (`provider=deezer` или без параметра `provider`).

### Запуск только на loopback

Откройте отдельное окно PowerShell:

```powershell
cd E:\MusicStream
# Обязательно: не доверять X-Forwarded-For даже от loopback-процесса.
# Переменная действует только в этом окне PowerShell и дочерних процессах.
$env:UVICORN_PROXY_HEADERS = "false"
uv run uvicorn musicstream.public_api:app --host 127.0.0.1 --port 8001
```

**Не используйте `--host 0.0.0.0`, `--reload` или несколько workers для этого
запуска.** Для явного задания того же поведения через CLI можно добавить
`--no-proxy-headers`. Не включайте `--forwarded-allow-ips="*"`.
У Uvicorn есть доверие к loopback-прокси по умолчанию; указанное отключение
proxy headers необходимо, чтобы произвольный `X-Forwarded-For` не менял
адрес клиента перед передачей запроса приложению.

```powershell
Invoke-RestMethod 'http://127.0.0.1:8001/health'
Invoke-RestMethod 'http://127.0.0.1:8001/api/search?q=Rammstein&limit=2' | ConvertTo-Json -Depth 5
```

Запросы только локальные; эти команды не публикуют сервер в интернете.
Cloudflare Tunnel не установлен и не настроен, порты Windows и брандмауэр
не менялись. Конфигурация Pages и `MUSICSTREAM_API_BASE_URL` не меняются.
Когда туннель будет отдельно согласован, направлять его следует только на
`127.0.0.1:8001`, а не на приложение разработки на порту 8000.

### Ограничения публичного приложения

- `q`: от 1 до 200 символов до удаления крайних пробелов; пустой или
  состоящий из пробелов запрос даёт 422.
- `limit`: по умолчанию 10, допустимо 1–25. Неизвестный провайдер даёт 422.
- Сетевые операции HTTPX имеют таймаут 10 секунд; весь вызов поиска
  дополнительно ограничен 12 секундами. Таймаут даёт 504, сетевой сбой и
  некорректный ответ Deezer — 502, HTTP 429/5xx Deezer — 503.
  Внутренние исключения и содержимое ошибочного ответа Deezer не выдаются.
- Ограничитель допускает **30 HTTP-запросов за скользящие 60 секунд на один
  адрес клиента**, включая `/health`, ошибочные параметры и неизвестные
  маршруты. Затем отвечает 429 с `Retry-After`. Корректные CORS preflight
  обрабатываются отдельно и не расходуют этот лимит.
- Состояние ограничителя хранится в памяти одного процесса, ограничено
  10 000 клиентскими адресами и очищается по истечении окна. Если место
  занято активными адресами, новые получают 429 вместо сброса чужого лимита.
  Перезапуск сбрасывает квоты; несколько процессов не разделяют состояние.
- CORS разрешает только origin **`https://beskokotov.github.io`**, метод GET,
  без cookies/credentials. `Retry-After` доступен JavaScript. Origin не
  содержит путь `/MusicStream/`; другие сайты того же GitHub-пользователя
  имеют тот же origin. OPTIONS обслуживается для CORS preflight.

### Что останется небезопасным или ограниченным у временного туннеля

**CORS — не аутентификация.** API без авторизации доступен любому, кто знает
его URL, включая CLI и серверные программы без Origin. Секрет URL и открытый
ключ в JavaScript не дают контроля доступа; ключей и токенов во frontend нет.

Приложение не читает `X-Forwarded-For`, `Forwarded` или `CF-Connecting-IP`
для определения посетителя. При отключённых proxy headers запросы из будущего
туннеля будут иметь адрес локального коннектора: **все посетители разделят
одну квоту 30 запросов/мин**, а локальные запросы с того же адреса также её
расходуют. Это консервативная защита до отдельной настройки доверенного
прокси. Она не позволяет получить независимую квоту по реальному IP каждого
посетителя. Любое будущее доверие к proxy headers требует отдельной проверки
конкретного прокси и перезаписи им входящих заголовков.

Ограничитель не заменяет аутентификацию, защиту от DDoS и глобальное ограничение
параллельных запросов. Общая квота может быть исчерпана одним посетителем;
несколько адресов могут создавать суммарную нагрузку на Deezer и ваш ПК.
HTTPS туннеля защищает транспорт, но не ограничивает право вызывать поиск.

У временного Quick Tunnel меняется hostname при новом запуске и нет гарантии
доступности; выключение ПК, backend или коннектора прекращает работу поиска.
Такой режим подходит для тестирования, а не для постоянной публичной службы.
Для длительной публикации нужны отдельные решения по доступу, стабильному
адресу, лимитам на периметре и мониторингу. Сейчас они не подключаются.

Проверки запускаются общей командой `uv run pytest -q`: публичный поиск,
CORS, таймаут, 429, независимые клиентские квоты, игнорирование поддельных
заголовков, закрытые служебные пути и все прежние функции локального приложения.

Справка: [CORS в FastAPI](https://fastapi.tiangolo.com/tutorial/cors/),
[настройки Uvicorn](https://www.uvicorn.org/settings/),
[ограничения Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).


## Источники воспроизведения: YouTube и Hitmos

Метаданные поиска по-прежнему предоставляет Deezer. Новый независимый пакет
`audio_providers` отделяет описание записи (`RecordingReference`), поиск
кандидатов (`AudioProvider`), оценку совпадения (`matching`) и способ
воспроизведения (`youtube_iframe`, `html_audio` или `external_link`). Состояния источника:
`available`, `unavailable`, `error`, `external_player`.

### Использование веб-плеера

1. Найдите композицию и нажмите на её название.
2. Прочитайте условия и разрешите подключение YouTube. До согласия плеер и
   YouTube API в браузере не загружаются. Кнопка внешнего поиска открывает
   YouTube только по вашему нажатию.
3. Нажмите «Найти источник». При настроенном серверном ключе появятся
   кандидаты YouTube с названием, каналом, длительностью и оценкой совпадения.
   Проверьте запись и явно выберите видео.
4. **Без ключа** откройте поиск YouTube, выберите видео и вставьте его HTTPS-
   ссылку или 11-символьный ID в поле «Уже нашли видео?». Нажмите «Загрузить
   видео YouTube». Это ручной выбор, совпадение метаданных не проверено.
5. Нажмите Play в видимом YouTube-плеере или нижней панели. Play/Pause,
   громкость и доступная перемотка управляют самим IFrame Player API.
   Прогресс берётся из реального состояния плеера. Автовоспроизведения нет.

YouTube-плеер остаётся видимым, не перекрывается интерфейсом и имеет размер
не меньше 200×200. При скрытии вкладки или уходе плеера за пределы viewport
воспроизведение приостанавливается. При смене композиции или отзыве согласия
старый плеер уничтожается. Следующий/предыдущий трек пока не реализованы.

Ссылки принимаются только с `youtube.com`, `www.youtube.com`, `m.youtube.com`
и `youtu.be` (watch, shorts, embed). Они разбираются в браузере до video ID;
сервер не загружает URL пользователя. Работают только обычные возможности
YouTube: региональные, возрастные ограничения, запрет embedding, удалённые
видео и ошибки сети не обходятся. Ошибки, включая YouTube 100/101/150/153,
показываются пользователю. Если встроенное воспроизведение недоступно,
видео можно открыть на YouTube. `explicit_lyrics: false` от Deezer не
используется как подтверждение версии видео или отсутствия цензуры.

### Серверный YouTube Data API (необязательно)

Создайте доступ к YouTube Data API v3 в своём Google Cloud-проекте и
ограничьте ключ этим API и подходящими серверными ограничениями. Ключ
задать только в окружении backend, без записи в исходники:

```powershell
$youtubeKey = Read-Host "YouTube Data API key" -AsSecureString
$env:YOUTUBE_API_KEY = [System.Net.NetworkCredential]::new("", $youtubeKey).Password
$env:UVICORN_PROXY_HEADERS = "false"
uv run uvicorn musicstream.public_api:app --host 127.0.0.1 --port 8001
```

Эти команды работают в Windows PowerShell 5.1 и PowerShell 7. Файл `.env`
автоматически не загружается. После изменения ключа перезапустите backend.
Отсутствие ключа — штатный режим с внешним поиском и ручным выбором видео.
Ключ не нужен для самого IFrame Player API, не выдаётся API-клиенту и не
попадает в статическую сборку. Поиск и подробности видео расходуют квоты
Google-проекта; ограничения квоты могут отличаться в зависимости от проекта.

Новый проверяемый маршрут в локальном и публичном приложениях:

```text
GET /api/audio/resolve?title=Sonne&artist=Rammstein&duration_seconds=272&provider=youtube
```

`title`/`artist`: 1–200 символов, не только пробелы; длительность — 0–86400
секунд; provider — `youtube` или `hitmos`. Произвольные параметры вроде `url`
отклоняются. Маршрут ограничен 10 обращениями в минуту с адреса клиента;
публично также действует общий лимит 30 HTTP-запросов/мин и прежний CORS.
Proxy headers должны оставаться отключёнными до согласованной настройки
доверенного коннектора. Документация, статика и служебные пути в публичном
приложении по-прежнему закрыты.

Сервер обращается только к двум фиксированным HTTPS-путям на
`www.googleapis.com`. Редиректы не выполняются. Лимит ответа — 256 КиБ
после декомпрессии, таймаут операции — 5 секунд, всего resolve — 10 секунд,
параллельно не более двух запросов к источнику. Общий бюджет процесса —
20 внешних запросов/мин и 160/24 часа, не более двух на один resolve.
Бюджеты в памяти сбрасываются при перезапуске; они не заменяют защиту квоты
на стороне Google. Результаты и файлы музыки не сохраняются. Сервер не
ретранслирует и не скачивает аудио/видео; публичный адрес может передаваться браузеру для прямого воспроизведения.

### Совпадение записи

Нормализуются Unicode, регистр, пробелы и пунктуация; сравниваются название,
имя исполнителя в названии/канале, длительность (допуск max(5 сек, 3%)) и
признаки live/remix/cover/acoustic/clean/explicit/remaster и других версий.
`likely` означает вероятное совпадение по доступным метаданным, `uncertain` —
недостаток данных, `mismatch` — отличие названия, длительности или версии.
Канал YouTube не является доказательством исполнителя, а эвристика не
подтверждает оригинальную запись или права. Для mismatch автоматический
выбор в интерфейсе не предлагается; остаётся явный внешний переход.

### Hitmos: доступ и способ воспроизведения

Обычный Chrome получает HTTP 200 на главной, robots.txt и страницах записей,
хотя HTTPX получает 403 даже с User-Agent Chrome. Поскольку robots.txt
запрещает поиск с `q`, автоматический поиск не выполняется. Пользователь
выбирает запись на Hitmos и вставляет ссылку или числовой ID в MusicStream.
Адаптер читает разрешённую страницу записи, сравнивает метаданные и предлагает
выбрать прямой запуск публичного потока через HTML audio или открыть плеер
на сайте Hitmos. Серверная ретрансляция не реализована. Настройка optional
extra описана ниже; фактическая доступность зависит от ответа источника.

### Проверки

`uv run pytest -q` включает фиктивные ответы официального API, отсутствие
ключа, сравнение версий, запрет embedding, ошибки сети/квоты/JSON, редиректы,
размер ответа, SSRF-allowlist и ограничения нового маршрута в обоих приложениях.
Реальные проверки доступности источников выполняются отдельно; результаты
моков не доказывают доступность конкретного видео в регионе пользователя.

В реальном Chrome официальный учебный ролик YouTube `M7lc1UVf-VE` дошёл
до состояния PLAYING и позиции 0:09. Музыкальный ролик `StZcUAPRRac`
(Rammstein — Sonne) доступен через oEmbed, но встроенный плеер сообщил о
запрете встраивания; интерфейс обработал ограничение. Это показывает, что
наличие страницы или метаданных не гарантирует разрешённое воспроизведение.
Автопоиск с настоящим Data API key не проверен: ключ в окружении не задан.
При повторных сетевых проверках загрузка YouTube также прерывалась ошибками
подключения; интерфейс показал недоступность, а не состояние воспроизведения.

Сборка Pages содержит тот же HTML/CSS/app.js и публичный config.js; новые
секреты или серверные файлы не добавляются в allowlist. Настройки туннеля,
GitHub Pages и Windows автоматически не меняются. Обновление кода на Pages
требует отдельно разрешённых commit/push и workflow.

Документация: [IFrame Player API](https://developers.google.com/youtube/iframe_api_reference),
[YouTube search.list](https://developers.google.com/youtube/v3/docs/search/list),
[правила YouTube API](https://developers.google.com/youtube/terms/developer-policies).

### Настройка браузерного чтения Hitmos

Повторное исследование уточнило прежний результат: HTTPX (даже с User-Agent
Chrome) получает пустой 403, но обычный установленный Chrome без CAPTCHA
получает HTTP 200. Через него доступны `/robots.txt`, `/copyright` и страницы
`/song/<id>`. Обход CAPTCHA, авторизации, IP-ротация и медиапрокси не используются.

`robots.txt` запрещает `*q=*`, `*ref=*`, `/get/` и `/cover/`. Поэтому
автоматический поиск с `q` не выполняется. В интерфейсе откройте поиск
Hitmos по кнопке, выберите запись на сайте и вставьте её ссылку или ID
в поле Hitmos. Backend принимает только числовой `hitmos_id` длиной 1–12,
а не URL. Новый параметр используется только с `provider=hitmos`:

```text
/api/audio/resolve?title=Song&artist=Artist&provider=hitmos&hitmos_id=81423717
```

Для проверки метаданных через установленный Chrome включите optional extra
и настройку в отдельном окне PowerShell:

```powershell
cd E:\MusicStream
uv sync --extra hitmos
$env:HITMOS_BROWSER_ENABLED = "true"
$env:UVICORN_PROXY_HEADERS = "false"
uv run --extra hitmos uvicorn musicstream.public_api:app --host 127.0.0.1 --port 8001
```

Для локального `/app` используйте `uv run --extra hitmos uvicorn musicstream.main:app --host 127.0.0.1 --port 8000`
в окне с тем же `HITMOS_BROWSER_ENABLED`. На Windows этот браузерный режим
запускайте без `--reload` и нескольких workers: драйверу Chrome нужен Proactor loop.
Обычная локальная разработка без Hitmos сохраняет прежний `--reload`.
Браузеры не устанавливаются автоматически:
адаптер использует уже установленный Google Chrome. Без extra, Chrome или
настройки остаётся понятный внешний переход; отсутствие браузера не ломает поиск Deezer.

Чтение выполняется с отключёнными JavaScript и скачиваниями. Разрешены
документы `https://ru.hitmox.org/robots.txt` и конкретный `/song/<id>`.
Для выбранной записи дополнительно разрешён один штатный запрос плеера:
его ответ перехватывается на заголовках и отменяется до получения тела
или следования редиректу. Сторонние домены, scripts, images, iframe,
поисковые запросы и любые другие запросы media блокируются через CDP,
включая последующие запросы после редиректов. Robots проверяется заново;
при запрете страницы или недоступности robots адаптер прекращает чтение.
Лимиты: один браузер одновременно, пять проверок страниц в минуту на процесс,
256 КиБ на документ, максимум 10 секунд на весь resolve. Публичные лимиты
и CORS сохраняются. Chrome запускается с временным профилем без сохранённых
пользовательских cookies и не создаёт музыкальную библиотеку.

Из JSON-LD MusicRecording извлекаются только название, исполнитель и длительность;
`@id` обязан совпадать с запрошенной страницей. Используется прежняя проверка
совпадения и версий. Из публичного `data-musmeta` может извлекаться адрес
потока собственного плеера: HTTPS на ru.hitmox.org, /get/cuts/ с тем же ID
или /get/music/<8 цифр>/<имя>_<тот же ID>.mp3. Относительные адреса из
data-musmeta нормализуются только относительно https://ru.hitmox.org. Это промежуточный адрес, зависящий от контекста
страницы источника. Временный Chrome использует обычную гостевую сессию и
свой естественный Referer, получает штатный редирект и извлекает только
проверенный конечный HTTPS-адрес CDN. Значения cookies не выдаются клиенту,
заголовки авторизации не подставляются. Сервер не считывает аудиоответ и
не запрашивает файл на CDN. Ссылки download-кнопок не используются.

При отсутствии подходящей публичной ссылки результат Hitmos — `external_player`:
«Слушать на сайте Hitmos» открывает плеер источника в новой вкладке.
При найденной ссылке и допустимом совпадении кандидат содержит `html_audio`
и `stream_url`. Кнопка пробует прямое воспроизведение в браузере; наличие
ссылки в HTML не гарантирует, что источник отдаст аудио внешнему сайту. Подтверждённого официального embed/API и
разрешения на ретрансляцию не обнаружено. Отсутствие X-Frame-Options само по
себе не даёт разрешения встраивать или копировать музыку. Правообладательская
страница содержит процедуру удаления, а не лицензию для MusicStream.

Проверенная реальная запись `/song/81423717`: «Ты не бойся ночи», ENZRO,
219 секунд. Получение метаданных через браузер работает. Встроенный аудиоплеер
реализован и проверен на реальном CDN-потоке этой записи. Промежуточный
адрес нельзя переносить из HTML напрямую: он может вернуть страницу песни.
Проверки без сети входят в `uv run pytest -q`.


### Встроенный HTML audio: штатный CDN-адрес

После выбора записи Hitmos и проверки совпадения нажмите
«Попробовать воспроизвести в MusicStream». Backend разрешает промежуточный
адрес собственного плеера в обычной гостевой сессии источника и возвращает
конечный публичный CDN-адрес. Браузер посетителя запрашивает аудио напрямую
на CDN. FastAPI не ретранслирует музыку и не создаёт музыкальную библиотеку.

Исследование установило цепочку: страница песни → /get/cuts/… в контексте
Hitmos → HTTP 302 на CDN → HTTP 206 audio/mpeg. Ранее frontend получал первый
адрес, который при внешнем запросе возвращал страницу песни, а не звук.
Точные серверные проверки cookie/Referer по клиентскому наблюдению не
утверждаются: подтверждены работа штатного гостевого потока и доступность
конечного CDN из чистого браузера без cookies Hitmos.

Публичный player.js использует обычный jPlayer и данные `data-musmeta`;
дополнительного поиска по закрытому API, DRM-дешифрования, входа в аккаунт,
подмены Referer, копирования пользовательских cookies или отключения защиты
браузера для этого решения не потребовалось. Публичный адрес и техническая
доступность не заменяют права на использование произведения.

В резолвере разрешены только проверенные CDN: `cdn13.deliciousoranges.com`,
`cdn14.deliciousoranges.com`, `cdn11.deliciousoranges.com` с префиксом `/s1/get`
и `s4.deliciouspeaches.com` с префиксом `/get`. Форматы — cuts с тем же ID
в пути или music с 8-значной датой и тем же ID в конце имени .mp3. Query, fragment,
credentials, посторонние домены/порты и ID другой песни отклоняются.
Обычный browser route может не проверять все переходы после редиректа,
поэтому CDP Fetch проверяет запросы и ответы. Ответ промежуточного запроса
прерывается на заголовках; сам CDN-запрос из backend не отправляется.
При неизвестном CDN, другом ответе или невозможности разрешить адрес
сохраняется внешний переход. Внутренний HTML и cookies в API не выдаются.
Исходный промежуточный адрес не используется как запасной после ошибки.

Адрес хранится только в памяти текущего выбора, не в localStorage и не в
постоянной библиотеке. Если он устареет, повторите проверку записи.
Поиск Hitmos по q остаётся ручным, автоматического обхода robots нет.
Для браузерного режима нужны extra hitmos, установленный Chrome и
HITMOS_BROWSER_ENABLED=true; команды запуска приведены выше. Настройки
GitHub Pages, Cloudflare Tunnel и Windows не меняются автоматически.

HTMLAudioElement управляет Play/Pause, громкостью и реальным прогрессом;
перемотка доступна только при ненулевом seekable-диапазоне. Смена композиции
или источника останавливает звук и освобождает src. Ошибки и таймаут загрузки
не выдаются за воспроизведение. Состояние «Играет» задаёт событие playing.

Реально проверена полная цепочка: поиск Deezer в UI → выбор записи Hitmos
/song/81423717 → backend resolve → прямой CDN → HTML audio в MusicStream.
Получены audio/mpeg и HTTP 206, длительность 218,85 секунды; проверены пауза,
громкость 25%, перемотка на 60 секунд, продолжение после 61-й секунды и
остановка при переключении на YouTube. В браузере посетителя cookies Hitmos
отсутствовали. В конкретной выдаче Deezer кредиты исполнителей отличались,
поэтому UI честно оставил оценку uncertain: запись Hitmos выбрана явно,
а идентичность оригинальной записи не заявляется.

Все тесты запускаются `uv run --extra hitmos pytest -q`. Новые тесты проверяют
источник CDN-адреса, недопустимые Location, запрет получения тела аудио,
SSRF-ограничения CDP и отсутствие cookie/HTML/первого адреса в публичном ответе.
Неизвестные зеркала/CDN не добавляются автоматически. Для обновления
опубликованного frontend нужны отдельно согласованные commit/push и workflow.


### Диагностика Sonne: подтверждённые причины и исправления

Исследованы именно указанные записи Rammstein — Sonne. Во всех трёх случаях
метаданные Hitmos: название Sonne, исполнитель Rammstein, 272 секунды.
С эталоном Deezer 272 секунды разница равна 0, результат сопоставления likely,
причин отклонения нет. Ошибка была после сопоставления:

| ID Hitmos | Подтверждённая причина прежнего отказа |
| --- | --- |
| 57658982 | Источник выдаёт s4.deliciouspeaches.com/get/cuts/…, отсутствовавший в allowlist |
| 79306580 | Источник выдаёт cdn14.deliciousoranges.com/s1/get/cuts/…, раньше разрешался только cdn13 |
| 80274130 | В data-musmeta относительный /get/music/…, который старый парсер не принимал; затем CDN11 и формат /s1/get/music/… |

Все три реальных CDN ответили HTTP 206 audio/mpeg. Проверено воспроизведение
в браузере, а затем через обновлённый UI MusicStream; фактическая длительность
MP3 — около 272,44 / 272,44 / 272,12 секунды соответственно. Эти дробные
значения не были причиной отказа: сравниваются метаданные обеих записей (272 с).
Контрольная ENZRO остаётся доступна. SSL-проверка включена, механизм источника
не обходится, сервер не сохраняет и не ретранслирует музыку.

Допуски и алгоритм совпадения не ослаблены: прежние порог названия 0,86 и
допуск длительности max(5 с, 3%). Для 272 секунд это 8,16 с. Live/remix и другие
версии по-прежнему отклоняются. Совпадение метаданных не доказывает идентичность
мастера или ISRC; это отдельное ограничение эвристики.

Общее сообщение «поток отсутствует или запись не совпадает» заменено стадиями:
source_search, source_metadata, matching, stream_resolution, cdn_response,
browser_playback. Если метаданные совпали, но адрес не получен, причина относится
к stream_resolution и не выдаётся за mismatch. UI показывает название,
исполнителя, длительность обеих записей, разницу источник − каталог, прежний
допуск и каждую причину отклонения. Внешняя ссылка Hitmos остаётся доступной.

Для локальной разработки включите безопасную диагностику:

```powershell
cd E:\MusicStream
$env:HITMOS_BROWSER_ENABLED = "true"
$env:MUSICSTREAM_DIAGNOSTICS = "true"
uv run --extra hitmos uvicorn musicstream.main:app --host 127.0.0.1 --port 8000
```

Откройте /app. В разделе источника появится раскрываемая диагностика:
время resolve, HTTP-статусы robots/метаданных/выдачи редиректа, тип cuts/music,
относительность исходного адреса, результаты проверки адресов и известное имя
CDN. Неизвестный hostname заменяется на unapproved. Полные адреса потоков,
параметры подписей, заголовки, cookies и токены в диагностике не выводятся.
Консоль браузера содержит только этап, фиксированный код ошибки и числовые
MediaError/readyState/networkState, без объектов событий и src.

Диагностика по умолчанию отключена. В musicstream.public_api:app она не
выдаётся даже с MUSICSTREAM_DIAGNOSTICS=true; сравнение метаданных и понятные
этапы ошибок доступны обычным пользователям. Новых публичных маршрутов нет.

Важно различать redirect_status источника и HTTP-ответ самого CDN. Обычный
HTMLAudioElement не предоставляет странице точный HTTP-статус аудиозагрузки.
MediaError 2 классифицируется как проблема загрузки CDN; MediaError 3 —
декодирование; MediaError 4 — неподдержанный источник/формат, при котором
неаудиоответ CDN лишь возможен, но не доказан. NotAllowedError отдельно сообщает
о требовании действия пользователя. Для подтверждения HTTP-статуса используйте
Network браузера; приложение не объявляет неподтверждённые 403/SSL/CORS причиной.

Сценарии source HTTP error, отсутствующего/отклонённого адреса, версии Live,
разницы длительности, границ допусков, приватности диагностики и запрета её
публикации покрыты тестами. Проверка: uv run --extra hitmos pytest -q.
Настройки Pages, туннеля и Windows, commit/push и публикация в этой задаче
не выполнялись. Изменения backend и frontend нужно развернуть отдельно.

### Автоматический подбор Hitmos: API и фактическое ограничение

После выбора трека Deezer интерфейс автоматически вызывает существующий
`GET /api/audio/resolve` с `provider=hitmos`, названием, исполнителем,
`duration_seconds` и необязательным `explicit_lyrics`. Новых публичных
маршрутов нет. Старый API и выбор YouTube сохранены; в интерфейсе первым
источником теперь выбран Hitmos. Передача URL на backend не допускается.

На реальной проверке 13 ноября 2026 года `robots.txt` Hitmos вернул HTTP 200
и по-прежнему содержит `Disallow: *q=*` для `User-agent: *`. Поэтому адаптер
останавливается **до запроса поиска**: `reason=robots_disallowed`,
`stage=source_search`, пустой список кандидатов. Это ограничение источника,
а не отсутствие Sonne в каталоге. Реальное автоматическое нахождение
кандидатов и полный сценарий без ручной ссылки сейчас не подтверждены и
недоступны в рамках разрешённого доступа. Не используются альтернативные
написания поискового адреса, зеркала, обход блокировок или сторонняя выдача.

При разрешающей политике адаптер читает `/search?q=…`, извлекает ID общим
HTML-парсером и проверяет первые три страницы через существующие
`read_song` и `parse_song`. Весь документ ограничен 256 КиБ, адреса и
редиректы проверяются прежними списками разрешённых доменов. Реальная
разметка поисковой выдачи не проверялась из-за запрета; извлечение и
сопоставление проверены на фиктивных документах, не выдаваемых за живые.

Ответ содержит прежние `candidates`, оценки `likely/uncertain/mismatch`,
сравнения метаданных и причины отклонения, а также:

- `selection`: `automatic`, `choose` или `none`;
- `selected_id`: ID автоматически выбранной записи либо `null`;
- `candidate.selection_reason`: причина выбора или необходимости подтверждения.

Автовыбор разрешён только для единственного подходящего кандидата с
`likely` и точным совпадением нормализованных названия и исполнителя.
Прежний допуск длительности `max(5 с, 3%)` сохранён. Неизвестная длительность,
неподтверждённый исполнитель, несколько подходящих записей, непроверенные
дополнительные результаты или ошибка части метаданных запрещают автовыбор.
Одинаковая длительность не доказывает идентичность записи или мастера.
Live, Remix, Radio Edit, Explicit и Clean учитываются отдельно. Положительный
флаг Explicit требует подтверждения источником; `explicit_lyrics=false`
не трактуется как подтверждение Clean или оригинальной версии.

Подбор проверяет метаданные, а не доступность аудио. После выбора по Play
выполняется тот же `/api/audio/resolve` с числовым `hitmos_id`: резолвер заново
проверяет запись и получает свежий адрес. Только затем существующий HTML audio
пробует воспроизведение. До события `playing` интерфейс не сообщает, что звук
воспроизводится. Если поток недоступен, доступна ссылка на исходную запись.
При неоднозначности предлагается выбор; отклонённые версии не запускаются
встроенным плеером. Ручная вставка ссылки находится в закрытом по умолчанию
разделе «Дополнительно / Диагностика» и остаётся рабочим резервным сценарием.

Кэш подбора находится только в памяти процесса: максимум 64 записи,
60 секунд для результатов/отказа robots, 30 секунд для ошибок источника.
HTML, cookies, гостевые сессии и адреса потоков в нём не сохраняются.
Параллельный подбор ограничен одним запросом; одинаковые ожидающие запросы
переиспользуют результат. Очередь входит в общий таймаут API 10 секунд.
Сохранены ограничения: 10 запросов resolve в минуту с клиента, 5 операций
браузерного чтения в минуту от процесса, одна браузерная операция одновременно.
Один подбор расходует до четырёх операций, отдельный Play — ещё одну.
Кэш и ограничители не распределены между несколькими worker-процессами.

Локальная безопасная диагностика включается прежним
`MUSICSTREAM_DIAGNOSTICS=true`; публичное приложение её не раскрывает.
Для проверки используйте прежний запуск с `HITMOS_BROWSER_ENABLED=true` и
`uv run --extra hitmos uvicorn musicstream.main:app --host 127.0.0.1 --port 8000`.
В `/app` найдите Sonne и выберите трек: при текущих правилах появится явное
сообщение о запрете автоматического поиска. Ручной ввод перенесён под
«Дополнительно / Диагностика».

Проверки: `uv run --extra hitmos pytest -q`. Тесты не используют интернет:
покрыты подбор, версии, неоднозначность, кэш, отмена, предел кандидатов,
API обоих приложений и остановка браузера перед запрещённой навигацией.
Дополнительный браузерный тест UI работает с локальными фиктивными ответами;
без установленного Chrome/Playwright он пропускается. Реально проверены
отказ автоматического поиска по robots и сохранение ручного резолвинга Sonne.
GitHub Pages, Cloudflare Tunnel, конфигурация API frontend и Windows не изменялись;
commit, push и публикация не выполнялись.

### Общий подбор источников и повторное использование соответствий

После выбора трека по умолчанию используется «Автоподбор»: существующий
`/api/audio/resolve?provider=auto`. Hitmos и YouTube реализуют общий интерфейс
обнаружения метаданных и отдельную подготовку воспроизведения. Результат
содержит кандидатов, оценки и причины состояния каждого источника (`sources`),
`selection`, `selected_source` и `selected_id`. По Play проверяется только
выбранная запись. Старые вызовы с `provider=hitmos` / `provider=youtube` сохранены.

Автоматический поиск Hitmos по-прежнему запрещён его `robots.txt`; Hitmos.fm
также запрещает поисковые query-URL. Эти запреты не обходятся. Официальный
поиск YouTube доступен после настройки серверного `YOUTUBE_API_KEY` и согласия
пользователя. Без ключа или согласия интерфейс сообщает причину, предлагает
открыть исходный сервис или использовать «Дополнительно». YouTube IFrame
сохраняется видимым, аудиодорожки не извлекаются. Ключ не помещайте в JavaScript.

Успешная ручная проверка Hitmos теперь запоминает соответствие метаданных
на 10 минут в памяти backend. Повторно выберите ту же запись Deezer: её источник
будет выбран автоматически (`reused_match=true`), без нового ввода ссылки.
Адрес аудио не кэшируется: Play получает его заново и проверяет запись.
После перезапуска или истечения срока соответствие исчезает. Это не библиотека
и не гарантия доступности CDN или идентичности мастера.

Подробности анализа четырёх файлов HomeMusic, архитектуры, TTL, ограничений,
проверок и границ автоматизации: [docs/source-selection.md](docs/source-selection.md).
Исходный код HomeMusic не копировался; скачивание и серверные аудиокэши не добавлялись.

Локальный запуск остался прежним:

```powershell
cd E:\MusicStream
$env:HITMOS_BROWSER_ENABLED = "true"
uv run --extra hitmos uvicorn musicstream.main:app --host 127.0.0.1 --port 8000
```

Откройте `/app`, найдите композицию Deezer и выберите её. Для Hitmos один раз
используйте «Дополнительно / Диагностика», затем повторите выбор того же трека
и нажмите Play. Для YouTube настройте свой ключ на backend, перезапустите сервер
и отметьте согласие в интерфейсе. Реальный доступ зависит от API, сети и прав
на встраивание выбранного видео. Публичное приложение продолжает запускаться
только на `127.0.0.1:8001` прежней командой; настройки туннеля и Pages не менялись.

Проверка: `uv run --extra hitmos pytest -q`.

# Экспериментальные торрент-метаданные

На Windows x64 с Python 3.12 установите необязательную зависимость: `uv sync --extra torrent` (при использовании Hitmos: `uv sync --extra hitmos --extra torrent`). Обычный запуск MusicStream не создаёт BitTorrent-сессию.

Локальный `.torrent` можно просмотреть без сети:

```python
from musicstream.torrent import inspect_torrent, select_audio_file

metadata = inspect_torrent(r"C:\path\to\allowed.torrent")
for item in metadata.files:
    print(item.index, item.name, item.size, item.extension)
selected = select_audio_file(metadata, 0)  # только MP3, FLAC, OGG или M4A
```

`inspect_magnet(uri)` читает только поля URI и возвращает пустой список файлов. Только явный вызов `fetch_magnet_metadata(uri)` запрашивает метаданные у пиров. URL трекеров из magnet игнорируются; аудиоданные не запрашиваются. Без доступных пиров получение метаданных завершится по тайм-ауту. Настройки: `MUSICSTREAM_TORRENT_TEMP_DIR` для временного каталога и `MUSICSTREAM_TORRENT_CACHE_MAX_BYTES` (по умолчанию 16 МиБ) для максимального размера принимаемых метаданных. Временные файлы удаляются по завершении вызова.

Для экспериментальной передачи диапазонов используйте `TorrentSessionManager`. Он принимает локальный `.torrent`, индекс выбранного аудиофайла и только явно заданных пиров на `127.0.0.1` или `::1`. Сессия создаётся при входе в контекст; диапазон `[start, end)` отсчитывается от начала выбранного файла. Все пересекающие диапазон pieces получают приоритет 7, остальные — 0. Данные возвращаются после проверки pieces библиотекой. Piece на границе файлов может содержать байты соседнего файла. Трекеры, DHT, UPnP, NAT-PMP и LSD отключены; сессия слушает только loopback. Ограничения `max_sessions`, `max_connections` и `TorrentSettings.cache_max_bytes` задаются при создании менеджера. Дисковый бюджет делится между одновременными сессиями; после его исчерпания закройте контекст и откройте новый. Выход из контекста удаляет временные файлы.

```python
from musicstream.torrent import TorrentSessionManager

manager = TorrentSessionManager()
async with manager.open_torrent(r"C:\path\to\allowed.torrent", 0,
                                peers=(("127.0.0.1", 50000),)) as selected:
    chunk = await selected.read_range(0, 65536, timeout_seconds=10)
```

## Локальный HTTP Range для тестового альбома

Экспериментальный маршрут включается только при `MUSICSTREAM_TORRENT_HTTP_ENABLED=true` в локальном приложении. Сервер заранее регистрирует файлы по индексам; запросы не принимают пути, `.torrent` и magnet URI. `public_api.py` этот маршрут не подключает. Доступ разрешён только клиентам с loopback-адреса. Трекеры и DHT не используются.

В первом PowerShell-окне запустите локальный seeder для своих MP3 с разрешённым использованием:

```powershell
uv run --extra torrent python scripts/local_torrent_seeder.py test_media/TorrentTestAlbum
```

Он выведет путь к локальному `.torrent`, номера `track-0` и далее, а также `Loopback peer port`. Оставьте процесс запущенным. Во втором окне задайте выведенный порт и запустите локальный сервер:

```powershell
$env:MUSICSTREAM_TORRENT_HTTP_ENABLED = 'true'
$env:MUSICSTREAM_TORRENT_HTTP_SOURCE = (Resolve-Path 'test_media/TorrentTestAlbum.local.torrent').Path
$env:MUSICSTREAM_TORRENT_HTTP_FILE_INDEXES = '0,1,2,3,4'
$env:MUSICSTREAM_TORRENT_HTTP_PEER_PORT = '<Loopback peer port>'
$env:MUSICSTREAM_TORRENT_CACHE_MAX_BYTES = '67108864'
uv run --extra hitmos --extra torrent uvicorn musicstream.main:app --host 127.0.0.1 --port 8000
```

Откройте в браузере `http://127.0.0.1:8000/api/experimental/torrent/track-1`. В сетевой панели браузера запросы при перемотке должны получать `206` с `Content-Range`. `HEAD` и `GET` без Range возвращают `200`; некорректный или недоступный однодиапазонный `Range` возвращает `416` с `Content-Range: bytes */<размер>`. Тело ответа передаётся блоками по 64 КиБ; сессия сохраняется между запросами и закрывается после 30 секунд простоя. Поддерживается один диапазон за запрос. При нехватке дискового бюджета сессия обновляется после освобождения других потоков.
