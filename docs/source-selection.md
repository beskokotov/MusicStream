# Подбор источников MusicStream: разбор HomeMusic и собственная реализация

Текущая реализация: Hitmos напрямую запрашивает `/search?q=...` и не загружает или разбирает `robots.txt`. HTTP-ошибки остаются ошибками источника; SSRF, DNS, TLS, проверки перенаправлений, частоты запросов и CDN сохранены.

Исследован публичный репозиторий [HomeMusic-public](https://github.com/justman-1/HomeMusic-public),
ветка master, 13 ноября 2026 года. GitHub не определяет лицензию репозитория;
разрешение на перенос кода не подтверждено. Исходники не копировались в MusicStream,
не подключались как зависимость и не исполнялись. Ниже — анализ архитектуры.

| Файл HomeMusic | Наблюдаемый подход | Решение MusicStream |
| --- | --- | --- |
| [hitmoz.py](https://github.com/justman-1/HomeMusic-public/blob/master/hub/app/providers/hitmoz.py) | Поиск ограниченного числа страниц, отдельное уточнение метаданных записи, состояние доступности домена, лимиты запросов | Раздельные `discover` и `prepare`, HTML-парсер и сетевые ограничения; без автоматического перебора доменов |
| [hitmos_fm.py](https://github.com/justman-1/HomeMusic-public/blob/master/hub/app/providers/hitmos_fm.py) | Независимый адаптер с тем же контрактом кандидатов; собственный разбор выдачи и дополнение метаданных | Общий контракт источников; адаптер Hitmos.fm не добавлен в рабочий маршрут |
| [matching/select.py](https://github.com/justman-1/HomeMusic-public/blob/master/hub/app/matching/select.py) | Жёсткое отсеивание, ранжирование, отдельный вердикт автоматического выбора или подтверждения, сравнение с конкурентами | Общая оценка метаданных и консервативный выбор. Версии и длительность нельзя компенсировать большим баллом |
| [listen.py](https://github.com/justman-1/HomeMusic-public/blob/master/hub/app/listen.py) | Повторное использование выбора, объединение одновременных операций, предварительная подготовка, приоритет источников и отдельные ошибки недоступности | Короткие кэши в памяти, последовательный доступ к каждому провайдеру, параллельность между двумя провайдерами и подготовка только выбранной композиции |

В HomeMusic также реализованы скачивание, открытие/ретрансляция потоков,
серверные копии аудио и более длительное запоминание результатов. Эти механизмы
не перенесены: MusicStream не сохраняет и не передаёт аудиофайлы, YouTube
используется только через официальный Data API и видимый IFrame Player.
Эвристики дат загрузки, битрейта или совпадающего текстового отпечатка не
используются как доказательство оригинальной или нецензурированной записи.

## Этапы в MusicStream

1. Deezer возвращает каталог и метаданные.
2. После выбора композиции frontend вызывает `GET /api/audio/resolve?provider=auto`.
3. `SourceSelectionService` спрашивает разрешённые провайдеры через `discover`.
   Возвращаются `DiscoveryBatch` и `DiscoveredRecording`: только метаданные,
   идентификатор, внешний сервис и доступный тип плеера; без решений совпадения
   и без адресов аудио.
4. Общий `selection.rank_batch` применяет прежний `assess` и сортирует результаты.
   `match_score` — техническая оценка 0–1, не вероятность совпадения. Сохраняются
   данные обеих записей и причины отклонения. Приоритет статуса совпадения выше
   числовой оценки. Автовыбор требует единственного допустимого кандидата с
   точными нормализованными названием и исполнителем, известной положительной
   длительностью и полным результатом проверки. Ошибка части источников или
   несколько подходящих кандидатов требуют выбора пользователя.
5. По Play вызывается тот же endpoint с явным провайдером и числовым `hitmos_id`
   либо `candidate_id` YouTube. `prepare` заново проверяет запись. Hitmos выдаёт
   свежий разрешённый адрес; YouTube проверяется через `videos.list`, после чего
   загружается видимый IFrame. Событие плеера подтверждает фактическое воспроизведение.

Версии Live, Remix, Radio Edit, Explicit и Clean, пороги совпадения и проверки
URL сохранены. `explicit_lyrics=false` не считается доказательством Clean.
Две записи с одинаковыми метаданными остаются отдельными кандидатами: одинаковая
длительность и название не доказывают идентичность мастера или ISRC.

## Кэши и параллельность

- Общий кэш `DiscoveryBatch`: максимум 64 записи, 60 секунд для успешной выдачи,
  30 для недоступного автоматического поиска, 15 для ошибки провайдера.
- Ранее проверенное соответствие: максимум 64 записи, 10 минут. Сохраняются
  только проверенные backend метаданные и ID, без адреса потока, cookies или сессии.
  В ответе `reused_match=true` означает подтверждённые метаданные, а не
  подтверждённый звук. Неоднозначные/отличающиеся записи не запоминаются.
- Повторный подбор того же трека может использовать это соответствие без нового
  поиска Hitmos. Каждый Play всё равно проверяет источник заново. Если проверка
  перестала проходить, соответствие удаляется. Сообщить серверу произвольное
  «подтверждение» из браузера нельзя: отдельного такого маршрута нет.
- До двух операций обнаружения одновременно, максимум одна на провайдер.
  Одинаковые запросы, ожидающие провайдера, используют уже полученный кэш.
  Очередь включена в таймаут провайдера 8 секунд, весь endpoint ограничен 10 секундами.
- Ключ содержит точные название, исполнителя, длительность и трёхзначный флаг
  Explicit: неизвестно, false или true. Различающиеся версии и Explicit не объединяются.
- Это кэши одного процесса. Перезапуск очищает их; несколько workers не разделяют
  кэши и лимиты. Прежний небольшой кэш адаптера Hitmos и его бюджет 5 операций
  в минуту сохранены. Endpoint сохраняет лимит 10 обращений в минуту с клиента.

Предварительный подбор касается только выбранного трека и его метаданных,
а не всех результатов каталога. Аудио и YouTube IFrame заранее не загружаются.
При `allow_youtube=false` сервис не делает запросы YouTube и не выдаёт даже
запомненное соответствие YouTube. Пользователь управляет этим флагом через
существующее согласие в интерфейсе; серверный API-ключ не передаётся frontend.

## Исторические наблюдения об источниках и проверки

13 ноября 2026 года проверены правила источников с идентификатором приложения
`MusicStream/0.1.0`, без подмены под поискового робота или другое приложение:

Исторические наблюдения от 13 ноября 2026 года (текущая версия приложения больше не запрашивает и не разбирает этот файл):
- `ru.hitmox.org/robots.txt` вернул HTTP 200 с `Disallow: *q=*`. Прежний адаптер останавливался до поиска с `robots_disallowed`; gate и статус удалены.
- `rus.hitmos.fm/robots.txt` вернул HTTP 200 с `Disallow: /*?*`. Это сохранено только как историческое наблюдение; текущий код эти правила не проверяет.
- Официальный YouTube Data API поддерживает автоматический поиск при настроенном
  `YOUTUBE_API_KEY`. В проверяемом окружении ключ не задан; реальные поисковые
  запросы YouTube не выполнялись. Поиск, подготовка, ошибки, согласие и IFrame
  проверены на фиктивных ответах официального интерфейса.
- Реальный браузерный сценарий: Deezer → Sonne 272 с → отказ поиска Hitmos по
  robots → одна ручная проверка ID 57658982 → повторный выбор того же трека без
  ручного ввода → свежий резолвинг по Play → звук с CDN, пауза и громкость.
  Сохранение аудио и медиапрокси не использовались.

Первое полностью автоматическое нахождение неизвестной записи Hitmos сейчас
недоступно. Для ранее проверенной записи повторный сценарий без ссылки работает
в течение жизни соответствия. Для нового трека возможен официальный поиск
YouTube после настройки ключа и согласия; при неоднозначности нужен выбор видео,
но не вставка URL. Внешние ограничения YouTube, включая запрет встраивания,
географию, возраст и требования браузера к запуску, остаются действующими.

Все ручные ссылки находятся в раскрывающихся разделах «Дополнительно».
Внешние ссылки на сервисы доступны и при отказе автоматического поиска.
Локальная безопасная диагностика сохранена; публичный API её не раскрывает.

Проверка: `uv run --extra hitmos pytest -q`. Тесты используют фиктивные ответы
провайдеров и не обращаются в интернет; браузерные проверки требуют установленного
Chrome и optional extra `hitmos`, иначе пропускаются. Windows, GitHub Pages,
Cloudflare Tunnel и конфигурация API frontend не изменялись. Commit и push не выполнялись.
