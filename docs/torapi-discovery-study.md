# TorAPI → MusicStream: исследование и проект адаптера

Дата проверки: 13 ноября 2026 года. Это прототип обнаружения, без подключения к действующим провайдерам и плееру.

## Проверенные источники

- [README](https://github.com/Lifailon/TorAPI/blob/main/README.md), [исходник](https://github.com/Lifailon/TorAPI/blob/main/main.js), [OpenAPI](https://github.com/Lifailon/TorAPI/blob/main/swagger/swagger.json), [категории](https://github.com/Lifailon/TorAPI/blob/main/category.json), [примеры ответов](https://github.com/Lifailon/TorAPI/blob/main/docs.md), [лицензия MIT](https://github.com/Lifailon/TorAPI/blob/main/LICENSE).
- Основной публичный адрес `torapi.vercel.app` и оба зеркала из OpenAPI (`toruapi.vercel.app`, `rutorapi.vercel.app`) на ограниченный запрос поиска ответили HTTP 402 `DEPLOYMENT_DISABLED`. Живые ответы RuTracker не получены. Дополнительные пакеты и TorAPI не устанавливались.

## API и данные

| Назначение | Маршрут | Важные поля |
| --- | --- | --- |
| Категории | `GET /api/get/category/rutracker` | Статическое соответствие ID → название |
| Поиск | `GET /api/search/title/rutracker?query=...&category=...&page=0` | `Name`, `Id`, `Category`, `Size`, `Seeds`, `Peers`, `Url`, `Torrent` |
| Детали | `GET /api/search/id/rutracker?query=<ID>` | `Name`, `Hash`, `Magnet`, `Files[{Name,Size}]`, `Torrent` |

`query` — строковый поиск по названию раздачи, отдельных параметров artist/album/song нет. Можно подавать составные запросы «исполнитель альбом» и «исполнитель песня». Категории для музыки есть, например 428/429 (зарубежная поп-музыка lossy/lossless), 424/425 (отечественная поп-музыка), 1499 (саундтреки к сериалам lossy). ID должны быть конфигурационным allowlist, а не только результатом поиска подстроки «музыка»: в списке есть аудиокниги, музыкальное видео и софт. `page=all` в исходнике обходит до десяти страниц; для MusicStream нужен только `page=0` с ограниченным числом результатов.

У ответа поиска есть сидеры, но нет magnet и файлами он не располагает. У ответа по ID есть magnet, info hash и имена/размеры файлов, но нет индексов файлов и надёжного track ID. `Size` поиска — форматированная строка, `Files[].Size` может быть строкой числа; нормализация обязательна. Парсер списка файлов RuTracker в исходнике опирается на CSS `ul.ftree > li.dir > ul > li`, поэтому вложенные структуры и изменения HTML могут дать неполный список. В исходнике поля описания по ID ориентированы на видео и не дают надёжной длительности музыкальных треков.

## Проект адаптера

Изолированный прототип `TorApiDiscoveryProvider` находится в `src/musicstream/torrent/torapi_discovery.py`. Он делает только `search_title(query, category)` и `details(id)` через внедрённый `httpx.AsyncClient`, нормализует опубликованную JSON-форму и проверяет согласованность magnet и info hash. Он не создаёт libtorrent-сессию и не включён в маршруты или `SourceSelectionService`.

Для следующей итерации нужен отдельный тип discovery-кандидата: `(torrent_id, title, category, seeds, info_hash, magnet, file_hints, confidence, status)`. Нынешние `DiscoveryBatch`, `AudioCandidate` и `SourceSelectionService` допускают только `youtube`/`hitmos`, привязаны к URL воспроизведения и не содержат album. Подставлять torrent в их текущий контракт нельзя; сначала следует расширить модель кандидата и включать TorAPI только по явной локальной настройке.

Предлагаемый поток:

1. Взять `Track.artist`, `Track.album`, `Track.title`, `Track.duration_seconds` из Deezer. Поиск «исполнитель + альбом» в выбранных музыкальных категориях; если неудача — «исполнитель + название песни». Ограничить запросы, страницу и тайм-аут, кэшировать кратко, не опрашивать все категории подряд.
2. Отсеять видеокатегории, сборники и издания с несовместимыми версиями; ранжировать по совпадению исполнителя/альбома, формату, году, числу сидеров и признакам `lossy/lossless`. Сидеры — признак доступности, не доказательство совпадения.
3. Для нескольких лучших ID получить детали. По `Files` выделить MP3/FLAC/OGG/M4A, сопоставить нормализованное имя файла, номер дорожки и длительность (когда её можно установить). При нескольких близких вариантах требовать выбора пользователя.
4. После явного выбора получить проверенные torrent-метаданные из magnet или разрешённого `.torrent` и сопоставить `Files` с их реальными индексами по имени **и размеру**. `TorrentSessionManager` должен получать индекс именно из libtorrent, а не позицию в ответе TorAPI.
5. Только затем создать локальную playback-сессию. Не начинать передачу аудио при поиске или просмотре результатов.

## Совместимость и ограничения

`inspect_magnet()` MusicStream принимает URI TorAPI и извлекает info hash, но возвращает пустой список файлов: magnet сам по себе списка не содержит. `fetch_magnet_metadata()` предназначен для явного получения метаданных от пиров; на публичной раздаче он не проверялся. Текущий `TorrentSessionManager` принимает только локальный `.torrent` и явно заданного loopback-пира, поэтому **цепочка TorAPI magnet → публичные peers → Play сейчас не реализована**. Тест на собственной локальной раздаче подтвердил сопоставление формы `Files` с `.torrent` и выбор индекса MP3.

README TorAPI заявляет поиск/детали без пользовательской авторизации и регистрацию RuTracker только для прямой загрузки `.torrent`. Однако текущий исходник содержит встроенный session cookie для RuTracker: локальная копия зависит от доступности зеркал и работоспособности этой сессии. Это не гарантия доступа. Публичный экземпляр сейчас недоступен; локальный Node/Docker-вариант даёт контроль над временем ожидания и кэшем, но сам должен иметь доступ к RuTracker и поддерживаться при изменениях HTML. Лицензия MIT относится к коду TorAPI, не к правам на содержимое раздач. Условия RuTracker и права на конкретные записи требуют отдельной проверки до автоматического воспроизведения.
