# VK Playback V2: проверка аудиотранспорта

В MusicStream добавлен локальный диагностический MP3-транспорт. Он включается
только флагом `MUSICSTREAM_AUDIO_TRANSPORT_TEST=true`. Фикстура — синтетический
тон, созданный локально. Маршрут поддерживает GET, HEAD и одиночный byte range;
временные токены хранятся только в памяти процесса и истекают через две минуты.
Кнопка теста использует существующий `#hitmos-audio` и общие элементы MusicStream
для Play, Pause, Seek и Volume.

Эта проверка подтверждает транспорт MusicStream и декодирование MP3 браузером,
но не воспроизведение VK. Допустимый публичный способ передать поток VK во
внешний плеер не установлен. Схема VKCOM описывает поля `url` и `access_key`,
но не задаёт разрешённый внешний способ воспроизведения или проксирования.
Поэтому `VKAudioProvider.prepare()` сохраняет статус `playback_unavailable`.
Диагностический MP3 не меняет его; поиск VK и серверная авторизация браузера
остаются отдельным механизмом.

## VK Playback V3: сетевой наблюдатель

При `MUSICSTREAM_VK_ENABLED=true` доступны только с loopback:

- `POST /api/audio/vk/diagnostics/start` — подключить CDP Network observer к
  странице текущего VK Browser Reader на пять минут;
- `GET /api/audio/vk/diagnostics` — получить статусы и безопасные заголовки;
- `POST /api/audio/vk/diagnostics/stop` — остановить наблюдатель, не закрывая
  страницу или браузер Reader.

Снимок хранит только хост, тип ресурса, статусы, выбранные числовые/MIME
заголовки и флаги наличия Cookie/Authorization/Range. URL, query string и
значения секретных заголовков не сохраняются. EME-события и запросы key system
отмечаются как признаки DRM; отсутствие этих признаков само по себе не
доказывает отсутствие DRM.

Новая маршрутизация появляется только после перезапуска приложения. Поскольку
VK Reader держит авторизацию в контексте текущего процесса в памяти, перезапуск
закроет именно этот контекст; новая сессия может потребовать повторного входа.
Активировать наблюдатель во время работы старой версии API невозможно.
