# Hitmos HTTPX vs Browser Reader

Проверка выполнена на текущем коде `master` без запуска сервера и без изменения
рабочего Hitmos Browser Reader, Auto Play, Prowlarr или BitTorrent. Временные
скрипты используют только фиксированный `ru.hitmox.org`, публичную DNS-проверку,
проверяемый TLS, лимит Browser Reader 5 запросов/минуту и существующий
DNS-pinned `HitmosStreamProxy` для Range-пробы. CAPTCHA, Challenge, авторизация,
токены и нестандартные параметры не использовались.

## Результат HTTPX

Обычный HTTPX GET `/search?q=...` получил HTTP 403 для всех пяти запросов. Время
ответа было 369–477 мс в первом проходе и 397–610 мс в повторном. Каждый запрос
был одним GET без redirect-follow; страница, метаданные, player redirect и Range
не были доступны. После получения 403 не выполнялись запросы к деталям или медиа.
Экспериментальный скрипт теперь останавливается на первом 403 и помечает
оставшиеся случаи как пропущенные; `httpx-observed.json` сохраняет ранее
полученные измерения.

В процессе проверки обнаружено, что первоначальный прогон успел отправить все
пять точных поисковых запросов, а затем повторить их после 403. Он не менял
заголовки или URL для обхода отказа, но последующие запросы после первого 403
не были необходимы; скрипт исправлен, чтобы больше так не делать.

## Browser Reader: холодный и повторный проход

Reader был один и тот же; страницы создавались заново, сетевой кэш Chromium
отключён существующим кодом. Повторный проход поэтому показывает прогретый
процесс/соединение, а не кэш страницы приложения. Первая пара измерений
`search + detail/redirect/Range` завершалась до следующего запроса к этой же
композиции. Время detail включает HTML страницы записи, штатный player redirect
и Range-проверку существующим прокси.

| Композиция | Поиск cold / repeat, мс | Страница + player 302 cold / repeat, мс | Range cold / repeat, мс | Сквозное время cold / repeat, мс | Deezer / Hitmos, с | Range |
|---|---:|---:|---:|---:|---:|---|
| Rammstein — Sonne | 1676 / 1201 | 4210 / 2107 | 371 / 374 | 6277 / 3699 | 272 / 272 | 206 |
| Rammstein — Du hast | 1016 / 937 | 1017 / 1093 | 342 / 708 | 2394 / 2761 | 235 / 234 | 206 |
| Rammstein — Mutter | 967 / 923 | 1355 / 2095 | 370 / 417 | 2712 / 3453 | 268 / 269 | 206 |
| The Weeknd — Blinding Lights | 942 / 1091 | 1081 / 1074 | 449 / 420 | 2492 / 2601 | 200 / 202 | 206 |
| Кино — Группа крови | 1086 / 1067 | 999 / 1001 | 347 / 337 | 2449 / 2419 | 284 / 284 | 206 |

Среднее полное время — **3,26 с cold** и **2,99 с repeat**; медиана — **2,49 с**
и **2,76 с** соответственно. На cold Sonne пришлось 4,21 с внутри Browser
Reader, тогда как остальные четыре detail-запроса заняли 1,00–1,36 с. Разница
между cold и repeat неустойчива: ускорение процесса не означает ускорение каждого
запроса. Reader не кэширует страницу (Chromium HTTP cache выключен), но повторный
проход использует уже запущенный Chromium. Полученный Range ответ имел HTTP 206,
а прокси дополнительно проверил тип и аудио-сигнатуру. `readyState` и движение
`currentTime` в этом эксперименте не измерялись.

Подтверждённый путь использовал четыре GET на композицию: один поиск; два в
Browser Reader (HTML страницы и player-запрос с 302); один ограниченный CDN
Range-запрос прокси. Это число составлено из измеренных стадий/ответов; Browser
Reader не публикует сырой CDP-счётчик. Заблокированный запрос из другого frame
отменён до внешней отправки и в число не включён. HTTPX отправил только поисковый
GET и не дошёл до остальных операций.

Оперативная память для этого прогона отдельно не измерялась: `psutil` отсутствует,
а доступный процесс Chrome общий и не даёт достоверного RSS именно этого
временного запуска.

## Что страницы отдают без JavaScript

Текущий Browser Reader запускает Chromium с `java_script_enabled=False`. При этом
все пять поисковых страниц вернули HTTP 200, пять страниц композиций — HTTP 200,
каждый штатный player GET получил 302, а существующий прокси подтвердил Range 206.
Значит, JavaScript не требуется для проверенного пути поиска, чтения метаданных,
получения штатного redirect или проверки аудио Range.

- ID берётся из ссылки `/song/<числовой-id>` (также из `data-musid` типа
  `track-id-<id>`).
- Названия и исполнители уже вложены в поисковую HTML выдачу как `data-musmeta`;
  длительности в этих найденных записях не было.
- Страница `/song/<id>` содержит JSON-LD `MusicRecording` с названием,
  исполнителем и длительностью.
- Player URL находится в `data-musmeta.url`. Browser Reader создаёт обычный
  HTML audio элемент и наблюдает ответ штатного запроса `GET` с HTTP 302.
  Redirect проверяется существующим allowlist/DNS-контролем; Range выполняет
  текущий DNS-pinned прокси.

## Кандидаты и порядок выдачи

Холодный и повторный поиск вернули одинаковые ID в одинаковом порядке на всех
пяти запросах:

| Композиция | ID кандидатов Hitmos в порядке выдачи | Примечание |
|---|---|---|
| Sonne | `57658982`, `79306580`, `63122010`, `79410936`, `80274130` | №4 — Rammstein, Clawfinger |
| Du hast | `63121920`, `63121993`, `63261770`, `63261866`, `79409410` | В первых пяти title/artist совпадают с оригиналом |
| Mutter | `57658985`, `79422238`, `63122001`, `63261765`, `79811606` | №5 — Acoustic Version, другой исполнитель |
| Blinding Lights | `67509023`, `68894169`, `69215345`, `70922059`, `75940801` | №2–3 имеют дополнительных исполнителей |
| Группа крови | `79436285`, `55527245`, `79453684`, `79403109`, `48614878` | Первые три title/artist совпадают с запросом |

Первый результат имел точные title/artist во всех пяти выдачах. У Sonne и Mutter
также есть точные варианты среди следующих записей; у Blinding Lights №2–3
добавлены другие исполнители. Текущий код сначала ранжирует пять разобранных
результатов, затем уточняет не более трёх кандидатов, прошедших пороги точного
title/artist/version. У равных оценок сохраняется порядок источника, а числовой
ID не используется как критерий. Значит, порядок влияет на tie-break и на то,
какие из первых пяти вообще доступны; лимит «три» применяется к подходящим
кандидатам после ранжирования, а не механически к трём первым ID. Порядок в
холодном и повторном запросах не менялся; тест не доказывает, что Hitmos всегда
сохраняет его.

Длительности из JSON-LD отличаются от Deezer на 0–2 секунды. Во всех пяти
страницах совпали ожидаемые исполнитель и название; Range прошёл. Отдельное
сравнение всех альтернативных кандидатов, запуск Auto Play для каждой композиции
и browser playback с проверкой `readyState/currentTime` здесь не выполнялись.

## Можно ли заменить Chromium?

**Полностью заменить рабочий Browser Reader HTTPX в проверенных условиях пока
нельзя.** Прототип с обычным GET получил HTTP 403 уже на поиске. Причину отказа
(включая то, является ли это Challenge) из ответа не определяли, не проверяли
вариации заголовков и не пытались обходить ограничение. Не удалось подтвердить
HTTPX-получение поиска, страницы композиции, 302 или Range.

При этом **выполнение JavaScript не является установленной технической
необходимостью**: существующий Chromium Reader его отключает и успешно читает все
нужные данные. Статический HTML парсится текущими функциями `parse_search_ids`,
`parse_search_metadata` и `parse_song`; переиспользуемая HTTPX-часть могла бы
выполнять эти же стадии, если источник разрешает ей GET. Для аудио всё равно
нужно оставить существующий проверяющий redirect и общий Range-прокси. Отдельный
HTTP Adapter и конфигурационное переключение сейчас не подключались.

## Файлы эксперимента

- `probe.py` — HTTPX-прототип фиксированного origin, DNS pinning, запрет
  автоматических redirect и fail-closed обработка 403.
- `browser_repeat.py` — Browser Reader cold/repeat, запросы порционно в рамках
  существующего лимита и Range-проба через текущий прокси.
- `httpx-observed.json` — фактические HTTPX 403 замеры первого прогона.
- `browser-results.json` — результаты пяти композиций, cold и repeat.

Измерения сделаны напрямую, без второго процесса MusicStream и без обращения к
порту 8000. Изменены только новые файлы в `experiments/hitmos-http-resolver/`;
предшествующие изменённые tracked-файлы остались нетронуты. Commit/push не
выполнялись.
