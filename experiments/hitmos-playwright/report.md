# Эксперимент Playwright + Hitmos

Проверка выполнена 14 ноября 2026 года в отдельной папке, без изменения сервера MusicStream на порту 8000, Auto Play, Deezer, Prowlarr или BitTorrent. Playwright запускал Chromium через установленный Google Chrome с временным контекстом без сохранения профиля. Cookies, токены и прямые временные URL в результаты не записывались.

## Что делает текущий адаптер

Текущий `HitmosProvider` разделяет поиск и подготовку. Автоматический `discover()` без браузерного reader возвращает `manual_search_required`, а браузерный reader не делает автоматический поиск, если это запрещено `robots.txt`. Пользователь открывает поиск Hitmos, выбирает числовой ID записи, после чего `lookup()` повторно проверяет метаданные.

`HitmosBrowserReader` уже использует Playwright, но в другом режиме: временный Chromium запускается с JavaScript и загрузками выключенными, через CDP разрешаются только `robots.txt`, конкретная `/song/<id>` и один штатный media-запрос плеера. Из HTML извлекаются JSON-LD `MusicRecording` и `data-musmeta`. Первый hop `/get/...` не читается как аудио: адаптер наблюдает его redirect, проверяет разрешённый CDN и возвращает только проверенный конечный адрес. Затем обычный HTML `<audio>` в браузере посетителя запрашивает MP3 напрямую.

Отклонение отдельных записей объясняется проверкой, а не отсутствием страницы: несовпадение названия/исполнителя/версии, отсутствие корректного player URL, неожиданный ответ или redirect на CDN вне allowlist. В живом сравнении запись с redirect на `cdn3.deliciousoranges.com` получила `stream_redirect_not_allowed`, хотя сам сайт в браузере её проиграл. Это намеренное ограничение текущего адаптера, которое нельзя снимать в рамках эксперимента.

## Playwright через интерфейс сайта

Скрипт [probe.py](probe.py) открывает `https://ru.hitmox.org`, находит поле `q`, вводит запрос, выбирает лучший результат по тексту и отбрасывает признаки `live`, `remix`, `cover`, `karaoke`, `edit` и подобных версий. Затем он нажимает обычную кнопку Play, наблюдает Media-запросы и ждёт состояние `<audio>`.

| Запрос | Поиск | Первый аудиоответ после Play | Наблюдаемое воспроизведение | Доставка |
|---|---:|---:|---|---|
| Rammstein — Sonne | 1,68 с | 0,21 с | `readyState=4`, `currentTime>0`, поток не paused | MP3 |
| Ты не бойся ночи + ENZRO | 1,68 с | 0,21 с | `readyState=4`, `currentTime>0`, поток не paused | MP3 |

В обоих случаях цепочка была `ru.hitmox.org /get/...` → HTTP 302 → CDN → HTTP 206 `audio/mpeg`. Браузер использовал обычный URL `<audio>`, `MediaSource` не обнаружен, HLS `.m3u8` не обнаружен. Ответ CDN содержал `Content-Range`; первый hop в одном прогоне был запрошен с Range. Считались только типы и статусы, без полного URL.

Для русскоязычного запроса сайт отдал первый релевантный вариант с несколькими исполнителями в подписи результата; это показывает ограничение простого текстового ранжирования. Точный artist/title/duration всё равно нужно перепроверять до передачи записи плееру.

## Сравнение с текущим адаптером

Скрипт [compare_current.py](compare_current.py) запускал существующий `HitmosBrowserReader` на тех же типах записей и сохранял только статусы и диагностику.

| Запись | Текущий адаптер | Время resolve | Причина |
|---|---|---:|---|
| Rammstein — Sonne, ID 57658982 | `available`, `html_audio` | 1,78 с | CDN `s4.deliciouspeaches.com` разрешён, redirect проверен |
| Ты не бойся ночи — ENZRO, ID 81423717 | `available`, `html_audio` | 2,25 с | CDN `cdn13.deliciousoranges.com` разрешён, redirect проверен |
| Ты не бойся ночи — ENZRO, ID 82566825 | `external_player` | 1,63 с | redirect на `cdn3.deliciousoranges.com` отклонён allowlist |

Для третьей записи Playwright действительно получил `HTTP 206 audio/mpeg` и начал воспроизведение в самом сайте, но переносить этот адрес в MusicStream нельзя: текущая политика разрешает только проверенный набор CDN. Это не повод расширять allowlist автоматически.

Агрегированные изменения процессов Chrome во время временного Playwright-запуска составили примерно 2–3 дополнительных процесса, 364–398 МБ RSS и около 5–6 секунд накопленного CPU в наблюдаемых прогонах. Эти цифры включают уже работающие процессы Chrome Windows и поэтому являются верхней оценкой, а не чистым профилем одного экземпляра. После закрытия контекста постоянный браузер не остаётся.

## Ответы на вопросы

1. **Открывается ли Hitmos через Playwright?** Да, страница отдаёт HTTP 200 и доступно обычное поле поиска.
2. **Работает ли поиск?** Да. Поиск через интерфейс занимает около 1,7 с, но для одинаковых названий встречаются ремиксы, live, каверы и записи с несколькими исполнителями; требуется строгая повторная проверка метаданных.
3. **Срабатывает ли Play?** Да. В двух поисковых прогонах аудио начало двигаться, а в отдельном случае сайт воспроизвёл поток, который текущий адаптер отклоняет по allowlist.
4. **Как браузер получает аудио?** Обычный HTML Media Element получает MP3 через 302 с Hitmos на CDN и 206 с `Content-Range`. HLS и MediaSource не использовались.
5. **Можно ли передать поток существующему веб-плееру?** Для разрешённых CDN — уже да: это текущая схема `html_audio` с прямым браузерным запросом. Для неразрешённого или сессионно-зависимого redirect — нет без изменения политики и риска обхода ограничений.
6. **Быстрее ли это текущей интеграции?** Поиск UI быстрый, а первые аудиоданные после Play пришли примерно за 0,21 с. Но Playwright с полноценным UI потребляет сотни мегабайт и несколько процессов; текущий адаптер разрешает только метаданные и redirect, а воспроизведение оставляет браузеру. Поэтому постоянный Playwright не даёт убедительного системного выигрыша.
7. **Нужен ли Playwright постоянно?** Нет. Для текущего разрешённого потока достаточно обычного браузерного `<audio>` после ручного выбора и серверной проверки. Playwright оправдан как изолированный инструмент исследования или первоначального обнаружения; держать его постоянно ради каждой песни нецелесообразно.

## Ограничения и файлы

Эксперимент не обходил CAPTCHA, Cloudflare, авторизацию, DRM, cookies или ограничения CDN. Он не скачивал целые композиции и не изменял рабочую интеграцию. [results.json](results.json) содержит обезличенные сетевые факты, [current-adapter.json](current-adapter.json) — статусы существующего reader. Временные browser contexts закрываются после каждого случая.
